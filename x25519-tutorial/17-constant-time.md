# 第 17 章：常数时间与侧信道攻击

> 对应论文：全文（常数时间原则散见 §2.1、§3、§4.6、§4.7）与 RFC 7748 §7（Security Considerations）、Kocher 1996、Bernstein 2005

## 17.1 本章要回答的问题

前 16 章里，“常数时间”这个词反复出现——第 5 章说 `carry25519` 的分支只依赖公开变量，第 6 章说 `fadd`/`fsub` 无分支，第 8 章说 `finverse` 用固定序列，第 9 章说 `swap25519` 用掩码代替 `if`，第 12 章说 Montgomery 阶梯每轮操作相同，第 13 章说钳位强制满迭代。这些做法背后有一个统一的原因。本章把散落各处的讨论系统化，回答：

1. 为什么执行时间会泄露秘密？时序攻击到底怎么工作？
2. “常数时间”具体要防住哪些泄露渠道？X25519 的每个函数分别怎么防？
3. 如何验证一个实现是不是常数时间的？常数时间是否就绝对安全？

## 17.2 时序攻击的原理

1996 年，Paul Kocher 在 CRYPTO 上发表《Timing Attacks on Implementations of Diffie-Hellman, RSA, DSS, and Other Systems》，第一次系统论证：**如果运算时间依赖于秘密值，攻击者可以用统计方法恢复秘密**。

核心观察：真实 CPU 上，一条指令的执行时间并非恒定。加法的进位、乘法的操作数大小、分支是否跳转、缓存是否命中，都会造成纳秒到微秒级的差异。这些差异虽然微小，但攻击者可以让对方用**同一个秘密**反复执行操作（例如 TLS 握手中用同一个私钥签名），并精确测量每次耗时；再对不同猜测做同样的测量，与观察到的耗时分布比对，就能逐步收敛到真实秘密。Kocher 的论文对 RSA 和 Diffie-Hellman 都给出了具体的攻击实例。

对 X25519 而言，秘密是私钥 `k`（255 位）。实现中任何“依赖 `k` 的某一位才执行的操作”，都会把这一位的值烙进执行时间。例如：

```c
if (k_bit == 1) do_something();   /* 灾难：k_bit 为 1 时多花时间 */
```

攻击者测量几千次标量乘法的时间，就能判断私钥的每一位。这就是为什么前 16 章如此强调“分支只能由公开信息决定”。

## 17.3 三大泄露渠道

常数时间实现要同时堵住三个渠道：

1. **分支（branch）**：`if (secret) { A } else { B }` 让 A、B 的执行时间不同。CPU 的分支预测器还会留下可观察的痕迹。**对策**：用算术运算代替分支——第 9 章的 `swap25519` 用 `c & (p[i] ^ q[i])` 的掩码技巧；`pack25519` 用“算出 $t-p$，非负才采用”代替 `if (t >= p) t -= p;`。
2. **缓存（cache）**：如果程序根据秘密值访问内存地址（如查表 `table[secret_byte]`），第一次访问会把该地址载入缓存、后续访问变快；攻击者通过测量自己代码的访问时间（或共享缓存的冲突）推断对方访问了哪个地址。**对策**：数组索引只用公开常量——`field_elem` 的 16 个元素访问都是 `out[i]`（i 是公开循环变量）；绝不写 `table[secret]`。
3. **指令延迟**：现代 CPU 上乘法、除法等指令的耗时可能随操作数变化（尤其老式 CPU 的微码除法）。**对策**：固定运算序列——第 8 章 `finverse` 固定 254 次平方 + 252 次乘法；第 12 章阶梯每轮固定 10 次 `fmul` + 8 次加减。

Bernstein 2005 年对 AES 的缓存时序攻击（《Cache-timing attacks on AES》）展示了渠道 2 的威力：标准查表实现只需少量测量就能恢复密钥。X25519 全部使用固定小数组和常数运算序列，从设计上避免了这三类问题——这正是论文选用 TweetNaCl 实现的原因之一（论文 §2.1：TweetNaCl“使用常数时间算法来防止侧信道攻击，即不基于秘密值进行分支或数组查找”）。

## 17.4 X25519 的常数时间全景图

把前 16 章的结论汇总成一张表——每个函数靠什么做到常数时间：

| 函数 | 潜在泄露点 | 常数时间手段 | 章节 |
|------|-----------|--------------|------|
| `fadd`/`fsub` | 无 | 16 次循环，无分支，无数据依赖索引 | 6.2 |
| `fmul` | 无 | 固定 16×16 长乘法 + 固定归约 + 两次 `carry25519` | 7.2–7.5 |
| `carry25519` | `if (i < 15)` | 分支只依赖公开循环变量 `i` | 5.5 |
| `finverse` | 循环次数随输入变化 | 固定 254 次迭代；`if (i != 2 && i != 4)` 只依赖公开的 `i` | 8.4–8.5 |
| `swap25519` | `if (bit)` 交换 | 掩码 `c & (p[i]^q[i])` 无分支 | 9.3 |
| `pack25519` | `if (t >= p)` 条件减法 | 算 $t-p$、非负才采纳，外层固定两次循环 | 9.4 |
| `montgomery_ladder` | 每轮随比特分支 | 每轮固定“一次差分加法 + 一次倍增”；比特差异用 `swap25519` 消除 | 12.3、12.6 |
| `clamp` | 无 | 纯位运算 | 13.3 |
| `x25519` | 输出全零检查 | `is_all_zero` 用 OR 累加而非 `memcmp` | 14.5 |

注意表中“只依赖公开的 `i`”反复出现。这是全书的铁律：**循环变量、常数值是公开信息，可以安全地用于分支；秘密数据只能通过算术和位运算处理。**私钥 `k` 的所有比特都通过 `swap25519`（算术）和固定迭代（无分支）消费，从不进入任何 `if` 条件。

## 17.5 常见实现错误

从零实现 X25519 时最容易犯的错误（都曾在真实库中出现过）：

1. **条件减法**：`if (t >= p) t -= p;`——正确但非常数时间（见 9.4 的替代方案）。
2. **动态调用次数**：`while (有进位) carry25519(x);`——调用次数随数据变化。必须固定为两次或三次。
3. **用 `memcmp` 比较秘密**：`memcmp(shared, expected, 32)` 在第一个不等的字节处提前返回。用固定时间比较（如 `acc |= a[i] ^ b[i]`）。
4. **查表**：`table[secret_byte]`——缓存泄露。X25519 不需要任何查表。
5. **提前返回**：检查到错误（如全零输出）立即 `return`，而错误路径比正常路径短——同样泄露信息。错误处理本身也要常数时间。
6. **钳位遗漏**：不执行 `k[31] |= 64`，导致实现“偷懒”跳过阶梯首轮（第 13.3 节）。钳位三个比特缺一不可。
7. **编译器优化破坏**：`-O2` 可能把看似无分支的代码重排。密码学实现通常用 `volatile`、内联汇编或专门的常数时间基元（如 `cswap` 宏）约束编译器；本教程的教学代码假设编译器不破坏常数时间性质（实际工程中需额外注意）。

## 17.6 如何验证

验证常数时间有三层手段，由浅入深：

1. **代码审查**：逐函数检查“有没有依赖秘密的分支 / 数据依赖索引 / 动态循环次数”。第 17.4 节的表就是审查清单。这是本教程覆盖的层次。
2. **时序测量**：在目标机器上对同一输入重复执行并统计耗时分布。常数时间实现应得到近似相同的分布；非常数时间实现会出现明显的双峰或分组（对应秘密位 0/1）。测量要排除噪声（关掉频率调节、固定 CPU、多次采样）。
3. **自动化工具**：dudect（“dude, is my code constant time?”，Reparaz–Balasch–Verbauwhede 2017）对随机输入做大量测量，用统计检验（Welch's t-test）判断执行时间是否与输入相关。OpenSSL、libsodium 等库都用这类工具做回归测试。

## 17.7 局限性：常数时间是必要不充分条件

常数时间消除了“软件层”的时间依赖，但**不等于绝对安全**：

- **微架构侧信道**：即使指令序列固定，现代 CPU 的推测执行、乱序执行、缓存预取仍可能造成数据相关的微时间差（Spectre、Meltdown 及其变体属于这一类）。防御它们需要更底层的措施（如 `lfence`、刷新缓存），超出本教程范围。
- **共享环境**：云主机、超线程上，攻击者与受害者共享物理核/缓存，可能通过缓存占用（Prime+Probe 等）恢复受害者的访问模式。X25519 的固定小数组对这类攻击相对不敏感，但仍非免疫。
- **物理攻击**：功耗、电磁辐射（差分功耗分析 DPA）是另一类侧信道。常数时间不防 DPA；防 DPA 需要掩码（masking）等对策。
- **协议层**：即使原语是常数时间，协议实现（错误消息、会话恢复、长度字段）也可能泄露。RFC 7748 §7 提醒：X25519 的调用者还应固定时间地处理所有错误路径。

一句话总结：**常数时间是密码学实现的最低要求，不是全部**。它保证“秘密不会通过执行时间流出”，但完整的安全还需要考虑微架构、物理和协议层面的威胁。

## 17.9 小结

- 时序攻击（Kocher 1996）利用“执行时间依赖秘密”来恢复秘密；X25519 的私钥每一位都必须被常数时间地消费。
- 三大泄露渠道：分支、缓存、指令延迟；对策分别是用算术代替分支、只做固定索引、固定运算序列。
- X25519 的每个函数都有明确的常数时间手段（17.4 节全景表），铁律是“分支只能由公开信息决定”。
- 验证手段从代码审查、时序测量到 dudect 等工具；常数时间是必要不充分条件，微架构、物理与协议层威胁仍需警惕。
